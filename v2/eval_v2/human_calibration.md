## 解讀

- judge 量的是 rubric 定義的「規範上的多餘」（重複的 successfully、目的子句、onboarding 的效益句、應為空的備註被填滿）；使用者量的是「真的煩人的多餘」（憑空多出的主張、多餘的指示）。兩者的 κ 低，意味著 judge 的絕對多餘率不能當成使用者感受的估計；arm 之間的**相對**差異仍可用，但要以人工結果為主。
- 在這批一般性題目上，control 被使用者判 0/12。抱怨的案例（安裝程式的「算了」、照片備註的「碗與叉子不計入營養」）在這裡沒有重現，暗示痛點集中在特定元件（備註／自由文字）與 app 自己的欄位指令，而非模型普遍多話。第二批盲評針對這個假設。
- 樣本小（每 arm 6–15 條），元件偏向按鈕與標籤；第二批改抽備註、說明、錯誤、狀態、數值，並以 judge 判定分層（各半）。

## 兩批合計的解讀

- 108 條盲評，使用者判多餘 4 條（3.7%），缺資訊 0 條；control 25 條全部 0。judge（rubric 為 v1 教義的嚴格讀法）與使用者的一致性兩批皆接近零。
- 使用者實際在意的是：捏造的主張（4 條中 3 條）、多餘的指示（1 條）。文案規範會刪的「successfully」「目的子句」「效益句」「教練語氣」，使用者在盲評時不在意。
- 因此：judge 的絕對「多餘率」不能當使用者感受；arm 之間的相對比較只能說明「對規範嚴格讀法的服從度」。使用者提出的痛點案例（算了、裝好了、碗與叉子不計入）在這 32 題一般性 held-out 題目上**幾乎沒有重現**——它們來自特定工具的特定 prompt（安裝程式由 agent 生成；照片備註的 topic 式欄位指令）。
- 對 skill 的含義：優先順序應為 語言 → 事實 → 不捏造 → 元件形式；「刪多餘」限於控制項、狀態與備註的樣板句，且以 linter 做 CI 檢查，不當成寫作教義的主體。
